## One root cause is already identified (a test defect), fix it properly

`recovery.rs:337` panics with `reconciliation emits InstanceRemoved`. The test calls `restart_with(...)`, which builds a service whose reconciliation starts at once on its runtime, and only THEN calls `restarted.receiver()` with the comment "Subscribe after the restart so the reconciliation events are observable". A `tokio::sync::broadcast` receiver sees only events sent after it subscribes, so when the reconciliation wins the race the event is gone; under 4-core contention it wins one run in a dozen. Same class: `Harness::run(op)` (`harness.rs:146`) subscribes AFTER `delete_instance`/`start_instance` returned (17 call sites use `.run(`; the safe `run_call` is used by 9), so `OperationFinished` can be emitted before the receiver exists and `finished_result(&events, &op)` is `None`.

Rules for the fix: (a) do NOT weaken assertions. Your round-1/2 edits in `instance/tests/coverage.rs` and `races.rs` accept `h.service.is_operation_finished(&op)` instead of the event, which turns "the delete must fail" into "the operation finished and a row exists"; revert them and fix the ordering instead. (b) Either subscribe before the operation starts everywhere (convert the 17 `.run(` call sites to `run_call`, and give `restart_with` a variant that hands back the receiver created before reconciliation starts, or a hook that starts reconciliation after the caller subscribed), or make the service keep the finished result of an operation in its registry (`operation_result(&op) -> Option<Result<..>>`, which is also useful to the GUI quit flow that now waits for stop completion) and have `run` return it; pick one, justify it in a paragraph, and make `Harness::run` impossible to misuse. (c) The "row never removed" timeouts (`harness.rs:738`, 62 s) are not lag: a delete that does not complete in 60 s is a hang or a lost wakeup. Capture it: on the deadline, dump the instance row, the in-flight marker and the operation registry into the panic message, loop `safety::two_concurrent_deletes_remove_the_instance_once` alone under the same env until it fails, and decide whether it is a product race in concurrent delete (then fix the product and say so loudly) or a test artifact (two services in ONE process share one pid, so an in-flight marker that trusts "pid alive" or "pid is mine" can never tell them apart: look at how the marker compares identity).

## ETXTBSY work: keep only what the logs justify

The other claim in your doc comments is wrong: an atomic write (temp file + rename) does NOT prevent ETXTBSY, because the busy state belongs to the inode and a forked child that inherited the temp file's descriptor keeps it open until it execs, whatever the file is called; only the retry (or not forking while a script is being written) helps.
