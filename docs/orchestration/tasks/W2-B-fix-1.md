## Q1 (HIGH) — "Hentikan semua lalu keluar" quits before anything is stopped

Real run: Quit from the tray, dialog, click "Hentikan semua lalu keluar". The window closed at once and the app exited. Two minutes later `postgres -D ...` was still running and listening on 5432, no "shutdown" line in the engine log, and `state.db` said `stopping` for the instance. (The next launch repaired the row to `running`, so that part of F-INS-04 works.) F-TRY-02 AC2 is not met.

Cause (read, then confirmed by the run): `DblService::stop_instance` returns `Result<OperationId>`; it only ENQUEUES the stop. `quit_flow.rs::handle_quit_action` treats `result.is_ok()` as `QuitEvent::StopFinished { ok: true }`, so the machine reaches `Done` and `cx.quit()` runs while the stop is still in flight inside this process. Your quit tests pass because the fake service stops instantly.

Fix: `StopFinished` must come from the OPERATION finishing (`UiEvent` `OperationFinished` for that operation id, or the instance reaching `Stopped`/`Failed`), never from the request being accepted. A request that is rejected (`Err`) is a failed stop. Bound the wait (the engine grace is `consts::STOP_GRACE_SECS`; use that plus a margin, from the constant, not a literal): on timeout the machine goes to `StopFailed` and offers "Keluar sekarang". The dialog shows `UI_QUIT_STOPPING` while pending (it already has the text) and the buttons stay disabled except the force-exit. Tests (red first, paste the red run): a service wrapper whose `stop_instance` returns at once and whose operation finishes 300 ms later through the event channel: `cx.quit` must NOT have happened before the finish event and must have happened after it; a wrapper whose operation finishes with an error: the machine ends in `StopFailed`, no quit; a wrapper whose operation never finishes: `StopFailed` after the bounded wait (use an injectable duration so the test takes milliseconds). Update `quit.rs` unit tests if the event model changes. Mutation: make `StopFinished` fire on request acceptance again: the first test must go red.

## Q2 (HIGH) — closing the window does nothing on Linux when a tray exists

`handle_window_close_request` calls `cx.hide()` and `cx.activate(true)` (tray "Buka DBLocal"). In the GPUI version we ship those two are NOT implemented on Linux: `gpui-pre-linux-0.3.12/src/linux/platform.rs`: `fn hide(&self) { log::info!("hide is not implemented on Linux, ignoring the call") }` and the same for `activate`. `on_window_should_close` returns `false`, so with a tray present the close button / WM close request is swallowed: real run, a WM close request (`wmctrl -i -c`) left the window on screen and the app alive. F-TRY-02 AC1 ("menutup jendela: app tetap hidup di tray") is not met, and "Buka DBLocal" cannot work either.

Fix (the design is yours, within these constraints): with a tray present, closing the window really closes it and the process, the service, the tray and the event bridge keep running; "Buka DBLocal" opens a NEW window and attaches it to the same service (the UI state is derived from the service, a fresh `Workspace` is acceptable; remember the open tab only if it is cheap). That means the tray handle, the tray pump, the service bridge and the quit machine must be owned at application level, not by the `Workspace` of one window. `gpui-pre 0.3.12` has `Application::with_quit_mode` / `App::set_quit_mode`; use an explicit quit mode so closing the last window does not end the process, and read `on_window_closed`. Without a tray (or when it vanishes), closing the window goes through the quit flow as today. Check macOS and Windows semantics in the GPUI source you can read and state them in `gui.md` (you cannot run them). Tests: pure/headless tests for the decision (tray present -> window closes and the app stays; tray absent -> quit flow), for "open while a window is open focuses it instead of opening a second one", and for the tray action reaching a freshly opened window. The reviewer repeats the real-window run for this.

## Q3 (HIGH, Windows and macOS) — the Linux preflights run on every OS

`lib.rs::run` calls `vulkan::preflight()` unconditionally. `vulkan.rs` looks for `/usr/share/vulkan/icd.d`, `/etc/vulkan/icd.d`, `~/.local/share/vulkan/icd.d` and asks wgpu for VULKAN adapters; on Windows (DirectX) and macOS (Metal) none of that exists, so the app would print the Linux "Vulkan not available / sudo dnf install mesa-vulkan-drivers" report and exit with code 78 before opening any window. `has_display()` only checks `WAYLAND_DISPLAY`/`DISPLAY`, which Windows and macOS never set, so `gui_unavailable_reason()` answers "no Wayland or X11 display" and `dblocal` with no arguments never starts the GUI there. Both date from wave 1 and were never exercised off Linux; the user will test Windows by rebooting this machine, so the first launch would fail.

Fix: gate by platform with `cfg`, expressed as small pure functions that take the OS as a parameter so Linux can test every branch: the Vulkan preflight applies to Linux (and the BSDs) only, the display check applies to Linux/BSD only and is `true` on Windows and macOS. Keep the `DBLOCAL_GUI_HEADLESS` flag and the main-thread rule as they are. Tests: for each of `linux`, `macos`, `windows` the preflight is skipped/applied and the display check returns what it must. Also grep `crates/gui`, `crates/cli`, `crates/core` for other Linux-only assumptions that run on every OS at startup (hard-coded `/usr`, `/proc`, `XDG_*` without a fallback, `HOME` instead of `USERPROFILE`) and either fix them or list them in the report.
