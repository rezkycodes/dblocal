Same branch `rezkycodes/w3-mariadb`, same worktree, rules `docs/orchestration/tasks/_COMMON-RULES.md` incl. 11-14. Earlier specs: `W3-B2-mariadb.md`, `W3-B2-resume-1.md`.

Your `worker_done` (outcome failed) was honest and the reviewer thanks you for not claiming clean runs. But you called the install-db failures "unrelated to my adapter": they are not. Reading your own logs: `Could not remove temporary table: '/home/rezkycodes/.cache/dblocal-e2e-tmp/#sql-temptable-2b4700-1-3', error: 2` followed by `ERROR: 1051 Unknown table 'mysql.tmp_user_sys'` and `Aborting`. mariadbd removes the `#sql*` temp files it finds in its `tmpdir` at startup. With no `tmpdir` configured, every server and every bootstrap on the machine shares `$TMPDIR` (or `/tmp`), so one mariadbd starting deletes the live temp tables of another one that is bootstrapping or running. It also fails at load 5-6 in your own logs, always in `mariadb_two_instances_side_by_side`, because five tests run in parallel. For users this is worse than a flaky test: a DBLocal MariaDB instance starting would delete the temp tables of a system MariaDB or of a second DBLocal instance (queries on those fail), and two instances created at once corrupt each other's bootstrap.

## S1 (HIGH) — every instance gets a private `tmpdir`

The path must stay short enough that nothing derived from it breaks (check: a temp file name is `#sql-temptable-...`, no socket lives there). The directory is removed with the instance; a leftover from a crashed run is emptied at the next start. ## S2 (HIGH on macOS) — the non-Linux identity check cannot match a path with a space

`identity.rs::verify_pid_identity_fallback` takes `ps -p <pid> -o command=` and does `cmd.split_whitespace()`, then treats the first token as the executable. The macOS data directory is `~/Library/Application Support/DBLocal/...`: the first token is `/Users/x/Library/Application`, `same_executable` says no, the result is `NotOurs`, `shutdown_by_sigterm` logs a warning and returns `Ok(())`. So on macOS EVERY MariaDB stop reports success without signalling anything and the engine keeps running (the pid and the port stay taken). It cannot be run here, but it is certain from the code. Fix: make the decision a pure function over the `ps` output string that never splits on whitespace: the command line starts with the expected executable path followed by a space or the end, and contains `--datadir=<expected>` or `--defaults-file=<expected>` as substrings followed by a space or the end. Prefer `proc_pidpath` through `libc`/`nix` for the executable when that crate is already a dependency of core (check `cargo tree -p dblocal-core -i libc`, do not add a dependency without saying so). Tests (Linux-runnable, they feed strings): an install path with spaces and `--datadir=/Users/x/Library/Application Support/DBLocal/instances/a/data` matches; the same path for another instance does not; a path that merely has the expected one as a prefix (`.../data2`) does not; a different binary does not. Mutation: put `split_whitespace` back -> the spaces test goes red.

## S3 (MEDIUM) — "unverifiable" must not report success

`PidIdentity::Unverifiable` (cannot read `/proc/<pid>/exe` or `cmdline` for a reason other than not found, `ps` failed to run) returns `Ok(())` from `shutdown_by_sigterm`: the engine may still be running and the caller marks the instance stopped. `NotOurs` and `NoSuchProcess` mean "our server is not running", `Unverifiable` means "I do not know". Return `Err(DblError::Engine)` naming the pid and the reason for `Unverifiable`. Test: a pid whose `/proc/<pid>/exe` cannot be read (permission) yields the error; mutation: back to `Ok(())` -> red.

## S5 (HIGH) — an instance that used the fallback socket directory cannot start after a reboot

Found by the reviewer reading `instance/start.rs` while checking your tmpdir/socket work: the start path never recreates the fallback socket directory or the private `tmpdir`. `initialize` creates `$XDG_RUNTIME_DIR/dblocal/` or `/tmp/dblocal-<uid>/` once and writes the socket path into `my.cnf`; after that `instance/start.rs::prepare` does nothing for this engine (`EngineKey::Mysql | EngineKey::Mariadb => Ok(())`, compare `prepare_postgres_run` and `prepare_valkey_run`, which recreate their directories on every start). Both fallback locations are volatile: `/run/user/<uid>` is a tmpfs wiped at logout/reboot and `/tmp` is cleared at boot (macOS clears `/private/tmp` at every boot). So an instance whose socket path needed the fallback (every instance on a long home, and on macOS the usual case) starts once and then FAILS to start after the first reboot: mysqld cannot bind a socket in a directory that no longer exists. The same holds for the per-instance `tmpdir` if its directory is missing (restored backup, cleaned run dir). Your deep-directory e2e does not see it because it initializes and starts in the same session.

Fix: a `prepare_run(ctx)` for the engine (in your engine module, called from `instance/start.rs::prepare` with a one-line change to that match; the other adapter's worker edits the same line, the reviewer resolves that conflict) that, on EVERY start, re-resolves the socket path from `my.cnf`, recreates and re-verifies the fallback socket directory (0700, our euid, not a symlink) when the socket lives there, removes a stale socket file left by a crash, recreates the private `tmpdir` (0700) and fails with a clear `Engine` error if it cannot. Tests (red first): pure (the prepare step recreates a missing fallback dir and a missing tmpdir, refuses a symlink and a wrong-mode directory, removes a stale socket file and leaves a regular file alone); real binary: initialize an instance in a deliberately deep directory, shut it down, delete the fallback socket directory and the `tmpdir`, then start it through the same path the service uses (`prepare` then `spawn_command`) and log in over TCP: it must work. Mutation: make `prepare` a no-op again -> that e2e goes red. Paste the red run.

(S1 stays the first priority; this one is a correctness defect, do it before the remaining coverage work.)
