# Common rules for every DBLocal worker (read before your task spec)

1. **Read `AGENTS.md` first**, then your task spec, then the architecture docs it names. The PRD is `docs/prd/dblocal/PRD.md`; decisions D-xx are in it.
2. **Commit within your first 30 minutes and after every meaningful step** (`git add -A && git commit`). A reboot and a dropped session have already cost one worker 2.5 hours of uncommitted work. Your worktree is under `~/orca/workspaces/db-local/`; `/tmp` is wiped on reboot, keep nothing important there.
3. **You cannot see images; never open one with the Read tool** (HTTP 422 ends your turn, and the image stays in the conversation, so every later request fails the same way: the session cannot be recovered and the reviewer has to restart you from the committed work; this includes screenshots from the cua tools: write them to /tmp and never read them; verify through the accessibility tree text instead). If you need pixels: `python3 -I /home/rezkycodes/Development/AI-Agent/db-local/scripts/review/ink_bands.py IMAGE X0 Y0 X1 Y1`.
4. **The machine is shared and tight.** ONE build cache for the whole project: core-only work uses `CARGO_TARGET_DIR=$HOME/.cache/dblocal-target`, work that links the GUI or the CLI crate uses `CARGO_TARGET_DIR=$HOME/.cache/dblocal-target-gui`. One cargo build at a time; never create another target directory; never leave a window, engine or background process running; report `df -h /` and `free -m` before and after your final gate. Several workers run at the same time on other files: stay inside the files you own, use `ask` with the exact change if you need anything else.
5. **Never touch the user's machine state**: no `sudo`, no installing packages or services, no writing outside your worktree, the build caches and temp directories you create. Engines in tests run only on ports 20000-29999 with a temp home.
6. **Quality bar** (every task): `cargo xtask ci` and `cargo deny check` green; pure logic >= 90% and every other touched file >= 80% line coverage (`cargo llvm-cov`, paste the numbers); files < 800 lines, functions < 50 lines, no `unwrap`/`expect` outside tests, no secrets in logs, errors typed and user-facing text in Indonesian with a stable `DBL-xxxx` code; tests loop 40 times in a row without a failure. Security-relevant rules get a mutation check: revert the rule, paste the red test output next to the test. A test is not evidence until it fails without the code it tests.
7. **Merge conflicts you cause are yours to expect, not to avoid by editing other people's files**: if you add a dependency, `Cargo.lock` changes; if you add `pub mod x;` to `lib.rs`, the coordinator resolves the trivial conflict at merge.
8. **Report** (send `worker_done`; if blocked send `ask`; never end your turn without one of the two): pasted `git log --oneline -5`, a clean `git status --short`, the largest `wc -l`, the coverage numbers, the 40x loop result, every defect you found with a minimal reproduction (a defect is a good result, do not hide it), and a list of what you could NOT verify (other OSes, real hardware, anything needing a human). Do not claim anything you did not run.
9. If the model API returns "500 Cannot connect to API" the session stops; the coordinator will tell you to continue. Everything you committed is safe.
10. **Never modify anything under `~/.cargo`, `~/.rustup` or any dependency source, not even "temporarily".** Those are shared by every worker and by the reviewer's builds. To investigate a dependency, copy it to a directory of yours under `~/.cache/` and point cargo at the copy with `--config 'patch.crates-io.<name>.path="<copy>"'` plus a separate `CARGO_TARGET_DIR`; never commit such a patch. A worker did this once, said it was restored, and it was not: the shared build cache had compiled the patched crate.
11. **Every fact in your report must be something you can paste.** A commit hash you did not copy from `git log`, a test count you did not copy from output, a "restored", "passed" or "clean" you did not verify: all are treated as false by the reviewer, who checks them (`git cat-file -t <hash>`, diffs against the original archive, a rerun of every gate). If a gate was not run, write "NOT RUN" and run it before you report done. Do not end your turn with failing or unrun gates: send `ask` with the blocker.
12. **Real-engine e2e runs are serialized machine-wide.** Several workers and the reviewer run `cargo xtask e2e` on this one machine; the tests use fixed ports (20000 and up), and `xtask e2e` scans the whole process table, so a second concurrent run makes both fail with "an engine outlived its test" or "a foreign listener holds port". Always run it through the lock: `flock -w 3600 "$HOME/.cache/dblocal-e2e.lock" cargo xtask e2e` (in the background with a log file, waiting on the log). If you ever saw "an engine outlived its test" for a pid that is not yours, another run overlapped: rerun under the lock, do not report it as a product failure and do not kill the other process. The same goes for any test that starts a real PostgreSQL, MySQL, MariaDB or Valkey: hold the lock for the whole run.
13. **Never end your turn to wait.** `ask` and keep working on everything that does not depend on the answer; an answered question does not wake a worker that has stopped. Ending your turn without `worker_done` or `ask` is the same as vanishing (two workers lost four hours each this way).
14. **Heavy gates are serialized machine-wide too, and the load is part of the evidence.** Six workers and the reviewer share this machine; at a load average of 20 the GPUI `render` test aborts with SIGABRT, engine shutdowns exceed their 20 s grace and timing-sensitive lib tests fail, and none of that says anything about your code. Run `cargo xtask ci`, `cargo llvm-cov` and any whole-lib loop of 20 or more runs under `flock -w 7200 $HOME/.cache/dblocal-heavy.lock <command>` (one at a time; do not hold the e2e lock and the heavy lock together), and for a gate that is sensitive to load (`render`, real-engine e2e) first wait until `awk '{print $1}' /proc/loadavg` is below 8 (poll with `timeout 900 bash -c 'until [ "$(awk "{print int(\$1)}" /proc/loadavg)" -lt 8 ]; do sleep 20; done'`; if it never gets there, say so in your report and keep the number). Paste the load average next to every gate result. A failure that only appears at load above 10 is not accepted as "pre-existing" by itself: reproduce it on `main` at the same load or show it passes quiet, and report it as a flake with the test name. If you want to create load on purpose (a flake hunt), pin it to ONE core (`taskset -c 0`, test and burners together) so the other workers keep their cores.
15. **Work ONLY inside your own worktree, on your own branch; never in the main checkout `~/Development/AI-Agent/db-local`, never commit to `main`.** Your terminal may start in, or `cd` into, the main checkout (after an API error and a "continue" it often does): check `pwd` and `git branch --show-current` before every edit and every commit; read files from the main checkout if you must, but write nowhere outside `~/orca/workspaces/db-local/<your worktree>`. **Never `git add -A`, `git add .` or `git commit -a`**: the main checkout holds the user's untracked prototype directory `dblocal-gpui-kit-source/` (never to be committed, edited or deleted); stage explicit paths (`git add crates/... docs/...`) and check `git status --short` before each commit. The reviewer merges into `main`, nobody else. (On 2026-11-23 a W4-B worker committed 20 prototype files and its work to `main` this way; the reviewer had to rewrite the local history.)
