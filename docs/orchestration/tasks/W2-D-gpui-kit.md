## Facts already established (verify, do not assume)

- `dblocal-gui` already depends on `gpui-pre =0.3.12`, `gpui-component =0.10.0` and `gpui-kit-assets 0.10.0`. GPUI Kit 0.10.0 documents exactly that stack, re-exported through one crate: `gpui-kit = "0.10.0"` with `use gpui_kit::*;` and `gpui_kit::component`, `gpui_kit::base`, `gpui_kit::assets`, `gpui_kit::platform`.
- Kit's Linux notes list `libxkbcommon-x11-dev`, which this Fedora host lacks (OPEN-03: X11 only passed `cargo check`). Whether the umbrella crate forces the X11 backend is the main unknown.
- Kit documents an optional `gpui-fast` feature (a different retained rendering and layout engine, `0.1.x`). It may change the idle RSS floor that OPEN-08 measured (empty GPUI window 165.4 MB, shell 178.6 MB, target < 150 MB). That is a hypothesis to measure, not a claim.

## Deliverables

1. **Migration to the umbrella crate.** Make `dblocal-gui` depend on `gpui-kit = "0.10.0"` (pinned exactly if Kit allows it, like the rest of the GPUI stack), drop the separate direct `gpui`, `gpui-component`, `gpui-kit-assets` edges, and switch imports to `gpui_kit::*` / `gpui_kit::component`. Keep the platform features (`wayland` default on Linux, optional `x11`, `font-kit` on macOS) working; if Kit exposes them differently, document the mapping. If the umbrella crate cannot build here (for example it forces X11 and `libxkbcommon-x11` is missing), do NOT install anything and do not hack around it: record the exact error, keep the current direct dependencies (they are the same crates and versions), write down precisely why in `docs/spikes/gpui-kit/README.md`, and continue with items 3 to 5 on the current stack. That is an acceptable result.
2. **Dependency and license check.** `cargo tree` diff before and after (new crates, duplicate versions), `cargo deny check` green (licenses, advisories, bans, sources), Cargo.lock keeps every package version main has for non-GUI crates (list the count before and after). Release binary size and cold start p50 over 20 runs, before and after, with the W0-C method.
3. **`gpui-fast` measurement (spike, not adoption).** Build the same shell with and without the `gpui-fast` feature and measure on this machine (Wayland, AMD RADV): empty window RSS, shell RSS, idle CPU over 60 s, cold start p50, release binary size. Use the measurement method of `docs/spikes/gpui/README.md` and say if you changed it. Then: do all render tests still pass, and what is the pixel difference against the committed PNGs (`docs/design/renders/`)? Does the GUI lib test suite pass 40 times in a row? Does `gpui-fast` support Windows and macOS (read the docs, say what you could not verify)? What is its license and how old is the latest release? Do NOT enable `gpui-fast` by default. The decision belongs to the user; give a recommendation with the numbers.
4. **Design-guide audit.** Kit's `design-guides` page is normative ("must / should / may"). Audit the current shell against it and write a table in `docs/spikes/gpui-kit/README.md`: rule, where it applies, status (pass, deviation, not applicable), file. Pay special attention to: text exposed to accessibility (`Label`, not bare strings), hover-only actions, secondary commands in `DropdownMenu` / `ContextMenu`, `Button` for commands and links only for URLs, explicit focus ownership and tab order, minimum window size, density, visible hover / focus / selected / disabled / loading / error / offline / empty states, tokens instead of literal colours. Fix only deviations that need nothing but an import or a one-line constructor change; list every other one with an effort estimate for me. Do not redesign.
5. **Themes.** Kit ships bundled theme presets (Default Light/Dark, Catppuccin, Tokyo Night, and others). Verify that `gpui_kit::init(cx)` and our JSON themes (`crates/gui/assets/themes/*.json`, Atom One based, contrast-tested) coexist: ours is the default, the contrast table test still passes, nothing from Kit's presets leaks into the default look. Report whether letting the user pick one of Kit's presets later is cheap (what API, what it costs in binary size), without implementing it.
6. **Packaging and auto-update pages.** Kit documents `packaging` and `auto-update`. Read them and write five lines on whether they overlap with our own plan (PRD D-08 and F-PKG-04..05: deb/rpm/msi built by CI, self-update reading the Releases API with SHA-256 verification, disabled for package-manager installs). Do not adopt anything; I decide with the user.
