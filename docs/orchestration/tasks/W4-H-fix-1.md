## F1 (MEDIUM) — "Pulihkan konfigurasi dan mulai ulang" starts the instance even when the restore failed

`restore_config_now` (`crates/gui/src/app/config_actions.rs`) calls `service.start_instance` right after `service.config_restore` regardless of the restore result, and the comment above it says the opposite ("it runs only when the restore succeeded"). A failed restore (no backup left, `DBL-8604` busy, an IO error) therefore starts the engine on the broken file, and the start's own result is dropped when the restore failed. Your `a_failed_restore_is_reported_typed` calls `restore_and_restart` with a failing restore but never asserts the start count. Probe (red on `a6f4255`, in `~/.cache/dblocal-review/w4hr/probes.rs`, first test): script `config_restore = Err(..)`, call `restore_and_restart`, assert `counts().start_instance` did not move.
Do: start only when the restore returned `Ok`; report each failure typed and distinct (restore failed vs start failed after a good restore); replace the `Option<()>` parameter by a `bool` or a two-variant enum. Red first (paste), then green, plus the mirror test (restore ok then start fails: both visible, the restored file is not rolled back).

## F2 (MEDIUM) — a pending "Restart sekarang" survives a failed stop and later starts the instance by itself

`restart_after_apply` sets `config_restart_after_stop` and calls `stop_instance`; only the transition to `Stopped` consumes it (`events.rs`, `after_status_change`). If the stop fails (the instance stays `Running` or goes `Failed`), the flag stays set. The next time the user stops that instance by hand, the app starts it again. Probe (red on `a6f4255`, second test in `probes.rs`): Restart sekarang on a running instance, `OperationFinished` with an error, then `InstanceChanged(Stopped)`; assert no start.
Do: clear the pending restart as soon as it can no longer be the stop it waited for: the stop's operation finished with an error (match the `OperationId` that `stop_instance` returned, do not clear on any operation), or the instance left `Stopping` for anything but `Stopped`, or the instance was removed (already handled). Say which one you chose and why. Tests: failed stop, stop that ends `Failed`, two instances (a pending restart of A is not consumed by B's stop), and the existing happy path stays green.

## F7 (MEDIUM) — an edit of the file by anything but this window is never seen, and the re-read blanks the form

Reproduction (real binary, isolated home): GUI open on the Config tab of a stopped PostgreSQL, `dblocal config set pg-app max_connections=120` from a shell (the file now says 120): the tab keeps showing 250 for as long as the window lives. `ServiceEvent::ConfigChanged` is an in-process event, so the CLI, a second DBLocal and above all the external editor that "Buka file konfigurasi" opens (F-CFG-02, the whole point of that button) are invisible; `enter_config_tab` reads only when no view exists. The "File berubah di luar aplikasi" banner is therefore reachable only by this window's own restore. Two more things in the same code: `reload_config_bg` replaces `data` with `Loading`, and `render_config_card` draws nothing but "Memuat..." for that state, so every re-read (after each apply, each event) blanks the whole form and drops the focus of the field being typed in; and `rebase` raises `touched_outside` whenever an edit survives, even when the file did not change.
Do: (a) re-read on EVERY entry to the Config tab and when the window becomes active while the Config tab is visible (GPUI window activation observer; if it is not available in `gpui_kit`, say so and do the entry re-read plus a re-read when "Buka file konfigurasi" returns, with the reason); (b) keep rendering the last good view while a re-read is in flight (a `refreshing` flag next to `data`, the card shows the old rows, the controls are not blanked, the focused field keeps focus; "Memuat..." only when there is no view at all); (c) `rebase` raises `touched_outside` only when a value the user has an edit on, or any value, differs between the old and the new view, never when the read returned the same file; (d) `changed_pairs` compares against the CURRENT view (it does, after (a) it is fresh); a typed value equal to the file is not sent. Tests: external change seen on re-entry, same file twice does not raise the banner, a re-read keeps the typed text and the rows, `Loading` with no view still says "Memuat...".
