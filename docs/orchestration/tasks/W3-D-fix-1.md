## K1 (HIGH) — `logs -f --lines N` reprints old history, out of order

Real binary, real Valkey log of 16 lines: `dblocal logs probe -f --lines 2` printed the 2 requested lines, and 250 ms later printed 11 more lines taken from the start of the file (13 lines for `--lines 2`). Cause: `follow_tail` keeps `previous = initial` (the last N lines) but the next snapshot is `tail_logs(id, FOLLOW_WINDOW = 200)`; `overlap(old = last 2 lines, new = whole file)` compares the old tail with the new HEAD, finds no match (k = 0) and prints the entire window. It only looks right when `--lines` equals the window (the default 200 is the lucky case) or when the log is shorter than N.

Fix: take ONE snapshot with the follow window at the start (`snapshot = tail_logs(id, max(lines, FOLLOW_WINDOW))`), print only its last `lines` lines, and from then on diff snapshot against snapshot. Make the diff a pure function `new_lines(previous, next) -> &[String]` with these tests: (a) 20-line log, `--lines 2`: output after one tick is exactly the last 2 lines, nothing more; (b) one line appended: exactly 3 lines in total; (c) append of 5 lines while the window is full (rotation of the window): only the 5 new lines; (d) the file is truncated/rotated (new snapshot shares no line with the old one): print the new snapshot once, not nothing; (e) identical repeated lines (the same text 3 times in a row) are not swallowed when 1 more is appended: document the limit if it cannot be solved with only `tail_logs` (no timestamps are guaranteed) and say so in `cli.md`. Also: a failing `tail_logs` in `poll_tail` currently ends the follow silently with exit 0; a transient read error must keep the previous snapshot and retry, and only "instance no longer exists" ends the loop (say which in `cli.md`). Create the `ctrl_c()` future ONCE outside the loop (pinned) so a SIGINT that arrives while a poll runs is not dropped; this is hardening, not an observed bug.

Prove it on the real binary and paste: create a Valkey instance with the cached runtime (like `cli_e2e`), start it, run `logs -f --lines 2` for 2 seconds, SIGINT, count the lines (must be 2). Extend `cli_e2e` with this check, plus an append observed while following (use the real Valkey: `redis` client `CONFIG SET loglevel` or any command that logs, or write a line through `dblocal`'s own log file via the service if the engine does not log on demand).

## K2 (MEDIUM) — `start` treats `stopping` as "somebody else is starting it"

`start.rs` maps `InvalidTransition { from: "busy" | "starting" | "running" | "stopping" }` to the race LOSER: it prints `sudah berjalan` and waits for `Running`. For `stopping` that is wrong: another process is stopping the instance, `Running` will not come, and the command prints a false message and then waits until `--timeout` (default 60 s) and exits 4 (by reading the code; reproduce it with a test first and paste the red run). Correct behaviour: `busy`/`starting`/`running` stay the loser case; `stopping` is reported as a clear Indonesian message ("sedang dihentikan oleh proses lain") with exit 1, not a wait. The same question for `stop` when another process is already stopping (`InvalidTransition` from "stopping"/"stopped"): today it exits 2 (bad arguments); make it the idempotent success `sudah berhenti`/exit 0 for `stopped`, and a wait-then-exit-0 or a clear message for `stopping`. Tests drive a service wrapper like the one in `races.rs` for each concrete status, and the table of (command, concrete status) -> (exit, message) goes into `cli.md`.
