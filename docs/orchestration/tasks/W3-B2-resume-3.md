## E1 (HIGH, blocks the merge) — `mariadb_two_instances_side_by_side` fails under moderate load

Reviewer evidence, all under the e2e lock, default threads: 5 of 10 plain runs failed (loop 1: runs 1-4 failed at load 8, 10, 11, 22 and runs 5-6 passed; loop 2 with a port sampler: run 3 of 4 failed). Read the logs, do not trust this summary: `~/.cache/dblocal-review/w3b2-flake/e2e-run-1.log` .. `e2e-run-6.log`, `sample-run-1.log` .. `sample-run-4.log`, `ss.log` (a 100 ms sample of every socket on ports 43100-43130 with its owning pid), `sample-summary.txt`. The same test also failed once in the reviewer's llvm-cov run. Three failure modes:

1. `shutdown: cannot read pidfile .../r2-i0/s/data/mariadbd.pid: No such file or directory` (e2e line ~1035).
2. `shutdown: mariadbd pid N did not exit within 20s after SIGTERM`. `ss.log` shows pid N LISTENing on 43106 for the whole 20 s and a probe connection from `wait_tcp` stuck in CLOSE-WAIT: the server never accepted it, so SIGTERM arrived while mariadbd was still starting.
3. `init: mariadb password bootstrap failed ... [ERROR] Can't start server: Bind on TCP/IP port. Got error: 98: Address already in use` for port 43106, always round 0, thread 0, in three consecutive runs (loop 1, runs 2-4), right after a run that had ended with mode 1.

Cause of 1 and 2 (read from the logs): `wait_tcp` only proves that the kernel is listening (the accept queue exists as soon as `listen()` returns). The rounds then call `shutdown` immediately, with no SQL in between, so the SIGTERM can land before the pidfile exists or before the server is initialised. The product's definition of ready is the protocol greeting (`health_check` == `Ready`, then the pid from the pidfile); the tests do not use it. Fix: every e2e wait uses `adapter.health_check(..) == Health::Ready` AND the pidfile present (poll with a deadline, include the engine log tail in the failure message), and only then run SQL or call `shutdown`. Apply it to all seven tests, not only this one.

Cause of 3 is NOT established; find it with evidence (the sampler is `~/.cache/dblocal-review/w3b2-e2e-sample.sh`, copy it, run it around your loop). Suspects, both checkable: (a) a server left running by an earlier failed run: when a round thread panics, `h.join().expect(..)` ends the test while the other round thread (and its mariadbd) is still running, and its guard never runs; make every spawned server killed on every exit path (create the guard before the first assertion, use `std::thread::scope` or join all threads before propagating a panic); (b) the e2e ports 43100-43122 lie inside the Linux ephemeral range (`cat /proc/sys/net/ipv4/ip_local_port_range` = 32768 60999), so any outgoing connection can hold such a port; rule 5 says tests use 20000-29999, move every port of this file there. ## E2 (MEDIUM, product, new) — the password bootstrap server listens on the instance port with an empty root password

`build_bootstrap_command` starts the full server (`bind-address=127.0.0.1`, `port=<instance port>`): until the init file has run, `root@127.0.0.1` has no password and is reachable by any local user, and `initialize` fails if anything else holds the port at that moment (that is how failure mode 3 shows up, and it will happen to real users). Add `--skip-networking` to the bootstrap command (the socket from my.cnf stays; the init file and its `SHUTDOWN` do not need TCP). Verify on the real 11.8.10 that the bootstrap still works and still removes the init file. Tests: command-args test; e2e: a foreign listener holds the instance port during `initialize` -> init succeeds and the password works afterwards over TCP; mutation (paste red, restored): drop the flag -> that e2e is red.

## E3 (MEDIUM) — `tests_hardening::install_db_failure_removes_data_dir` is flaky

Failed once in the reviewer's `engine::mariadb` lib x20 loop (`80 passed; 1 failed; finished in 0.51s`), clean in 700 further runs of the same binary (so it is rare; the reviewer could not capture the message). It writes a fake `mariadb-install-db`, chmods it and executes it while sibling tests fork: the classic `ETXTBSY` (text file busy) race, the same class W3-B1 fixed in `4f4ca68`/`98725df` and W2-A in `d2815ff` (branch `rezkycodes/w2-flaky-instance`); with that error the message would be `failed to execute mariadb-install-db`, which makes the first assertion fail. Fix with one test helper used by EVERY test that writes and executes a fake binary (`grep -n 'from_mode(0o755)' crates/core/src/engine/mariadb/*.rs`): write to a temp name in the same directory, close, chmod, rename into place, and retry the execution on `ETXTBSY` a few times with a short sleep. Evidence: `engine::mariadb` lib x100 at default threads and x100 with `RUST_TEST_THREADS=32 taskset -c 0-1`, 0 failures.
