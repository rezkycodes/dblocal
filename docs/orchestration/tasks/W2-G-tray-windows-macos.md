## Situation

`start_tray()` returns `TrayStartup::none()` on Windows and macOS, so those two platforms degrade to the F-TRY-01 AC3 fallback ("Tray tidak tersedia", close = quit). The user verifies Windows by rebooting this dual-boot machine; nobody here can run macOS. So: you cannot run either backend. Everything you cannot run is written as "unverified" and becomes a checklist row; nothing is claimed.

## Deliverables

1. A backend per platform behind the existing `TrayBackend` trait, selected with `cfg(target_os = ...)`, the Linux module untouched. Prefer a maintained crate over hand-written FFI: evaluate `tray-icon` (with `muda` menus) first, and check `cargo deny check` (licenses, advisories, bans), the added crate count, and the release binary size delta (`ls -l` before/after, Linux build unaffected because the dependency is target-gated). Paste the evaluation (what you compared, what you rejected and why) in `gui.md`. Fall back to `windows-sys` / `objc2` directly only if the crate cannot meet the constraints below.
2. Constraints that are not negotiable: (a) the tray object is created and used on the thread that runs GPUI's event loop (macOS: main thread with AppKit; Windows: the thread with the message pump): read the GPUI source for each platform and state in `gui.md` which thread creates it and why that is the right one; (b) menu activations arrive on a channel and are forwarded to the existing flume action channel with a blocking `recv`, no timer, no polling, no `sleep` (OPEN-08: idle CPU); (c) the menu is the same `TrayMenuModel` as Linux (instances grouped by engine, start/stop with disabled states, "Buka DBLocal", "Keluar"), rebuilt only on instance/catalog events; (d) status dots: render `status_dot_argb` (or the RGBA conversion your crate needs) per status for menu icons where the platform supports menu item icons, and an aggregate tray icon (any `Failed` red, else any `Running` green, else grey); (e) failure to create the tray (no shell tray area on Windows, a restricted session) returns `TrayHandle::unavailable()` and the AC3 note, never a panic; (f) the app-level ownership from W2-B (tray handle in `AppRuntime`, one event bridge) stays as it is.
3. Pure code first and tested on Linux: the model-to-menu-spec translation per platform (labels, enabled flags, icon bytes, aggregate icon decision), the activation-id to `TrayAction` mapping, the failure paths with a fake backend that fails to create. Coverage 80%+ of the new pure code, 90%+ of the pure decisions.
4. Compile evidence you can produce here: `cargo check -p dblocal-gui --target x86_64-pc-windows-gnu` (the toolchain and a target dir exist: `~/.cache/dblocal-target-windows-gnu`; install nothing under `~/.cargo`, use what exists or say what is missing), and for macOS `cargo check` of the tray module with `--target aarch64-apple-darwin` if it builds without an SDK, otherwise a minimal crate that contains only the tray backend and says exactly why the full check is impossible.
