## Acceptance (PRD, verbatim intent)

- F-PLH-01 AC1: with only the keyboard the whole first session (choose engine -> create -> start -> copy URI) can be completed, **with the focus always visible**.
- F-PLH-01 AC2: the command palette (`Ctrl/Cmd+K`) finds an instance and runs start / stop / copy URI.
- F-PLH-02 AC1: the app follows the system light or dark theme and **all text meets 4.5:1**.
- F-PLH-02 AC2: instance status is never conveyed by colour alone (a text label or an accompanying icon always exists).

## Do

1. **Audit first, write the findings into `docs/dev/accessibility-checklist.md`** (a table: screen/state, what you checked, how, result, what is unverified). Cover every screen and dialog that exists on main: sidebar tree and filter, tabs, Overview (all cards and the failure banner), Logs, Databases (W4-B: tables, drop dialog, secret dialog, reset dialog), Config (W4-H), create dialog, delete dialog, quit dialog, Settings dialog, Open in… menu, palette, toasts, status bar, tray menu labels. For each: reachable by Tab / Shift+Tab in the visual order, activatable by Enter/Space, Escape closes the top overlay and returns focus to where it came from, no keyboard trap, the focus indicator is visible (a ring or outline of at least 3:1 against both the element and the background, not only a background tint).
2. **Fix what the audit finds**, small commits, one concern each, each with a headless GPUI test that fails first (dispatch real key events and assert which element holds focus, and that the focused element renders a focus indicator the theme guarantees). The first-session flow gets ONE end-to-end headless test driven only by key events through the scripted/mock service: open the create dialog (`Ctrl/Cmd+N`), pick an engine and version, name, create, start (`Ctrl/Cmd+Shift+S` or the Start button via Tab+Enter), copy the URI (`Ctrl/Cmd+Shift+C`), asserting the clipboard text and that no pointer event was used.
3. **Palette** (AC2): typing finds instances by name and engine, Up/Down/Enter choose, the start/stop/copy URI commands appear for the matching instance and are disabled with a reason (text) when not applicable (start on a running instance, and so on); Escape closes and returns focus. Test each.
4. **Theme and contrast** (AC1): `contrast_table.rs` already checks the token pairs; extend it so EVERY text/background pair the screens actually use is covered in BOTH themes, including the pairs W4-B and W4-H introduced (muted helper text, placeholder text, disabled controls' labels (WCAG exempts disabled text but the PRD says "seluruh teks": say what you decided and why), danger text, toast text, badge text on tinted backgrounds, link/active tab, focus ring vs surface). A pair that fails gets a lighter/darker token, not an exemption. A test that walks the render output is better than a hand list: if you can enumerate the colours the views request (the theme token accessors) and fail on any token pair that is used for text but not in the table, do that; otherwise say plainly which pairs are only covered by hand. **Following the system theme**: check how the app reads the system preference, that a change while running is applied (or document that it needs a restart), and that both themes render every screen (extend `crates/gui/tests/render.rs`). Do NOT change the user's real desktop theme setting to test (no `gsettings set`, no portal write): force the theme through the app's own override/environment/test hook; if none exists, add a small explicit one (`DBLOCAL_THEME=light|dark|system`, documented) and test it.
5. **Status never by colour alone** (AC2): audit every place a status shows (sidebar rows, tab glyphs, header badge, tray tooltip, status bar counters, Logs, failure banner, Config "perlu restart", Databases "superuser" badge) and make sure each carries text or a different shape/icon. A test that renders each status in greyscale-equivalent terms is not needed; a table test that every status variant maps to a non-empty label AND a distinct glyph is.
6. **Docs**: `docs/dev/accessibility-checklist.md` (the manual per-release checklist the PRD NFR names (line ~945), with what to press and what to expect, split into "automated here" and "manual on Windows/macOS"), and update `docs/architecture/gui.md` (focus model, the theme override, the contrast test).
