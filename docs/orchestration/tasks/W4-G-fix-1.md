## F1 (HIGH) — focus is lost whenever an overlay closes by confirming; the keyboard is then dead

`run_palette_action` (`workspace_api.rs`) sets `self.palette_open = false` and never calls `restore_dialog_focus_after_close()`; `submit_create` closes `self.create` on success without it. Check EVERY other way an overlay can end (delete confirm, Settings close, the admin dialogs and secret dialog, the restore confirmation, the quit dialog, the Open-in menu): one helper that every dismissal goes through, so a path cannot forget. When the opener captured nothing (focus was on no element when the dialog opened, as at startup) or its handle is gone, fall back to the Workspace root focus handle: the keyboard must never end with nothing focused.
Also startup: in the real window `ctrl+k`/`ctrl+n` did nothing before the first click (step 1). Under Xvfb there is no window manager, so say whether the root already takes gpui focus on the first frame; if it does not, make it (`window.focus(&root)` once, on the first render or in `Workspace::new`) and prove with a test that builds a fresh window and presses `ctrl-k` with no focus call before.
Red first (paste): key-driven tests, never a direct method call: palette `ctrl-k`, type, `enter`, then `ctrl-k` must open again and `window.focused` is `Some`; create via `enter` on Create, then `ctrl-n` opens again; delete confirm; Settings; each overlay kind you found. The existing `escape_returns_focus_to_the_opener` stays.

## F2 (MEDIUM) — Tab leaves the modal dialogs, and their own controls come last

PRD F-PLH-01 / the spec says "no keyboard trap" and "visual order"; a modal that lets Tab reach the page behind its scrim is the opposite problem (focus on an element the user cannot see, Enter on it acts on the page). Fix for the create dialog and for every other modal (delete, Settings, quit, restore confirmation, admin dialogs, secret dialog, palette): Tab and Shift+Tab cycle inside the dialog only, in visual order (engine cards -> version rows -> Nama -> Port -> checkbox -> Batal -> Create; the focus on open may stay on Nama). Tests: for each modal, Tab 40 times (and Shift+Tab 40 times) and assert that every focused handle belongs to the dialog's own subtree and that the cycle wraps; plus an order test for the create dialog. If gpui-component has a focus-scope or tab-group primitive, use it and say which; otherwise handle Tab in the dialog root.

## F3 (MEDIUM) — tests that do not pin what the report says they pin

The reviewer mutated `b0cf2c3` 14 times (GUI lib, a scratch copy). Eight are red (palette start enabled on a running instance, Escape not restoring focus on the create dialog, a status without a label, the palette Start arm doing nothing, `submit_create` doing nothing, the create dialog not taking focus on open, `DBLOCAL_THEME=dark` ignored, a token pair darkened below 4.5). **Six stay green.** The ones that matter most:
- Removing `focus_ring_style` from `apply_focus_ring` (the ring of every engine card and version row): **all 407 tests stay green**. The PRD acceptance is "focus always visible"; nothing asserts that a focused control draws a ring. Your mutation table claims the ring is covered by `keyboard_only_first_session`: that test only proves the control takes focus, not that it draws anything.
- `tab_stop(true)` -> `tab_stop(false)` on the same rows: **all 407 green**. The first-session test focuses the handles directly instead of reaching them with Tab; `tab_forward(10)` only asserts that something holds focus.
- `keyboard_only_first_session` ends at "create". The spec asked for: create, then START (`Ctrl+Shift+S` or the Start button via Tab+Enter) and COPY URI (`Ctrl+Shift+C`), asserting the **clipboard text**, with no pointer event. Start and copy are missing, and `service.calls() > 0` is already true from the calls made when the window is built (the test only goes red under "submit does nothing" through its dialog-closed assertion); assert the specific call (a per-method counter or a recorded argument list in `QuietService`: `create_instance` with the spec chosen by key, `start_instance` with that id, the URI).
- `palette_starts_an_instance_with_the_keyboard` sets the query and then calls `run_palette_action(index)` directly: the part that matters (Enter on the filtered row reports the right ORIGINAL index, a disabled row does nothing) is not exercised. It works in the real window, so this is only a missing pin: drive it with `press(cx, "enter")` and a query that leaves ONE row that is not the first of the unfiltered list.
Do: a test that fails when the ring is not drawn (a render/pixel check read by code in `tests/render.rs`: the focused card's edge pixels equal `theme.ring`, an unfocused one's do not; or a debug-selector bounds assertion; say which and why) for engine card, version row, Button and Input; Tab-reachability tests (F2's walk covers it); the full first session including start and the clipboard; the palette through Enter. The other green mutants, each needs a test or an honest note in the checklist why it cannot be tested headless: (a) the palette no longer focuses its query field on open (`open_palette` without `state.focus`): the palette still works only because the click focused something; (b) the palette's `keywords` dropped, so typing the ENGINE word (`postgres`) no longer finds an instance whose name does not say it: spec AC2 says "finds an instance by name and engine" and no test types an engine word through the CommandState; (c) the disabled palette row not marked `disabled(true)`: Enter on a disabled row must do nothing, drive it with keys; (d) `observe_window_appearance` never applying the theme (live following of the system theme): test it if the gpui test platform can change the window appearance, otherwise list it as manual in the checklist and say so.

## Xvfb recipe (works here; the desktop's Xwayland does not accept synthetic input)

```
Xvfb :77 -screen 0 1440x900x24 -nolisten tcp &        # pick a free display number
env -u WAYLAND_DISPLAY DISPLAY=:77 DBLOCAL_HOME=/tmp/dbl-x DBLOCAL_THEME=light setsid nohup <release dblocal> &
```
`env -u WAYLAND_DISPLAY` is mandatory: without it gpui opens the window on the USER's real Wayland desktop. There is no window manager: find the window with `xdotool search --name ""` (the 1280x820 one), `xdotool windowfocus <id>`, and click once on the page background (`xdotool mousemove 700 400 click 1`) before the first key; the click is part of what F1 must make unnecessary. Keys: `xdotool key --delay 150 ctrl+n`, `xdotool type`. Clipboard: `xclip -selection clipboard -o`. Screenshots: `import -window root -crop 1280x820+82+40 +repage /tmp/x.png` (the window sits at +82+40). You must NOT open the images (rule 3): detect the ring by code, for example the bounding box of what changed between two consecutive frames: `convert a.png b.png -compose difference -composite -threshold 0 -format %@ info:`; the reviewer reads the images himself. Pre-place `postgresql-18.7.0-x86_64-unknown-linux-gnu.tar.gz` from `~/.cache/dblocal-dev/` in `$DBLOCAL_HOME/downloads/`. Wait about 1.2 s after each key before the screenshot.
