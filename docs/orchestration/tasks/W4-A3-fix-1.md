## F2 (MEDIUM) — the docs say admin dials only a Running instance; the code never checks

`docs/architecture/admin.md`, "Residual risk of loopback TCP": "Admin only behaves this way after the caller has loaded a `Running` instance row; a stopped or failed instance's port is not dialled by an admin call in normal use". `admin_ops::with_admin` loads the row and goes straight to `executor_for`: no status check. So on Windows (and for PostgreSQL on every OS, which already dials `127.0.0.1:<port>`) `dblocal db list <stopped-instance>` hands the generated superuser password to whatever process now listens on that port (the user's own MySQL on 3306 is the obvious case: DBLocal checks the port is free at *start*, not later). On unix the MySQL socket is DBLocal's own path, so the risk is the TCP arms only.
Do: gate in `with_admin` (and the reset path if it loads the row separately): when the instance status is not `Running`, return the existing connect error (`AdminError::Connect`, `DBL-8100`, "Pastikan server sedang berjalan"), **before** `executor_for`, before any credential read and before any dial. Same code and message as today's behaviour for a stopped instance, so no caller changes. Tests with the fake executor factory: each of Stopped / Starting / Stopping / Failed returns that error and the factory is never called (assert the call count is 0, and that no credential was read), Running still reaches the executor; one per admin call (`list_databases`, `list_users`, `create_database`, `drop_database`, `create_user`, `reset_superuser_password`). Mutation (paste red): the gate removed. Then correct the doc sentence to what is true, state the remaining window (status says Running, then something else takes the port) and keep the "no post-connect identity check" note.
Check the existing service/e2e tests still pass: they must reach admin on a Running instance only. Say in the report if any test had to change and why.
